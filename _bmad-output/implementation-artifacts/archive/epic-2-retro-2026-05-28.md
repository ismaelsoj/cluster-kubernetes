## O Que Foi Difícil

### Story 2.1 — 20 erros de linter na primeira rodada
O kube-linter foi mais exigente do que esperado: `readOnlyRootFilesystem`, `runAsNonRoot`, limites de CPU/Memória, volumes emptyDir adicionais. Gerou iterações extras não planejadas.

### Story 2.1 — CrashLoopBackOff por mountPath do Postgres 18+
O Postgres 18+ mudou o comportamento de montagem: requer `/var/lib/postgresql`, não `/var/lib/postgresql/data`. O linter estático não detecta — só aparece em runtime. Debugar CrashLoopBackOff com logs confusos custou iterações.

### Story 2.1 — env expansion em exec probes
O Kubernetes não expande variáveis de ambiente (`$POSTGRES_USER`) em exec probes sem shell. O comando `pg_isready -U $POSTGRES_USER` rodava como literal, causando `role 'postgres' does not exist` nos logs. Fix: encapsular com `/bin/sh -c`.

### Story 2.3 — jboss-logging emite CLIENT_LOGIN em DEBUG por padrão
O AC exigia evento `CLIENT_LOGIN` nos logs JSON. O listener `jboss-logging` emite eventos de sucesso em nível `DEBUG` por padrão — invisível com configuração padrão do servidor. Necessária variável adicional `KC_SPI_EVENTS_LISTENER__JBOSS_LOGGING__SUCCESS_LEVEL=info`, não documentada de forma óbvia nas notas do Keycloak 26.

### Story 2.4 — História mais complexa para testar
Apesar de classificada como Baixa Complexidade, a 2.4 foi a mais difícil de validar: exigiu corrupção controlada do banco, janela com selfHeal desativado no ArgoCD e sequência precisa de comandos. A documentação correta foi determinante — sem ela, o processo seria impraticável.

## Insights-Chave

### Insight 1 — Linter ≠ Runtime
O kube-linter captura estrutura e segurança estática, mas **não captura comportamento de imagens**. O `mountPath` do Postgres 18+, a expansão de variáveis em exec probes e o nível de log do `jboss-logging` são exemplos de coisas que o linter nunca detectará. O plano de validação manual em cluster vivo é tão obrigatório quanto o linter.

### Insight 2 — Code Review Late-Stage tem ROI alto mas requer atenção a ACs
Os patches de code review foram consistentemente valiosos. Porém, quando um patch altera o comportamento descrito em um AC, a spec precisa ser atualizada junto — caso contrário a documentação diverge da implementação.

### Insight 3 — Latest Tech Information deve incluir gotchas de versão
Gotchas de middleware (`jboss-logging` em DEBUG, `pg_isready` sem shell, `mountPath` do Postgres 18+) precisam de pesquisa prévia. O campo `Latest Tech Information` das specs existe exatamente para isso — quando bem usado (Story 2.3 com `--import-realm`), salvou iterações.

### Insight 4 — Multi-Model Review é um Padrão Saudável
Implementação com claude-sonnet-4-6 e revisão com GPT-5 Codex/Gemini gerou diversidade de perspectiva que fortaleceu os entregáveis. Vale manter como prática.

## Action Items

### AI-1 (Institucionalizado no BMad) — Verificação de Regressão de ACs no Code Review
Regra adicionada ao `bmad-code-review.toml`: antes de apresentar findings, verificar explicitamente se algum patch invalida um AC. Se sim: atualizar o AC na spec, listar ACs afetados e informar o usuário.

### AI-2 (Institucionalizado no BMad) — AC de Teste End-to-End Condicional
Regra adicionada ao `bmad-create-story.toml`: histórias que tocam o fluxo de bootstrap (cluster-up, inject-secrets, infra-app, root-app) recebem AC explícito de `make down && make up`. Histórias sem impacto no bootstrap (scripts isolados, docs, overlays) ficam isentas.

### AI-5 (Institucionalizado no BMad) — Spec Atualizada Quando AC É Modificado
Consolidado na mesma regra do AI-1 no `bmad-code-review.toml`: nunca aplicar patch que altere um AC sem atualizar o texto do AC na spec correspondente.

### AI-4 (Ativo) — Latest Tech Info Deve Incluir Gotchas de Versão
Na criação de cada história, o campo `Latest Tech Information` deve incluir gotchas conhecidos da versão específica do software.
